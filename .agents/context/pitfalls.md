# SmartPI pitfalls

Verified against branch `dev-0.7`. Paths are relative to `custom_components/vtherm_smartpi/`
unless they start with `tests/`. Format: symptom/trap -> why -> what to do.

## Regulation and integral

- Ki stuck at `KI_MIN` -> Ti = tau (1/b) makes Kp/Ti tiny -> `smartpi/gains.py` uses SIMC `Ti = min(tau, GAIN_TI_LAMBDA_FACTOR * (lambda + L))`; keep it.
- Gains take their delay from `smartpi/gains.py::start_dead_time` (reliable active dead time after a start; feeding them the model's theta + tau_e/2 + h/2 made them too soft, lot b4); the integral holds from `SmartPI.hold_dead_time_s` (`effective_dead_time`: theta + tau_e/2, else the same dead time). Do not read `dt_est` directly for either.
- Displayed integral jumps when the near-band taper moves Ki -> `algo.py` rescales `integral *= old_ki/new_ki` on any Ki change to keep `Ki*I` -> judge `u_i`/`Ki*I`, not the raw integral.
- 0.1 C sensor: reading on the setpoint level freezes the integral (deadband), one step above saturates low and skips integration -> offset of about half a step -> `smartpi/controller.py` allows `I:UNWIND(sat)` within `NEAR_SETPOINT_UNWIND_STEPS` x observed sensor step. Do not widen guard thresholds by a sensor step to fix it.
- Anti-windup `track_output_limit` back-calculates only in `smartpi/controller.py::_TRACKED_I_MODES` (`I:RUN/SKIP/CLAMP`); other modes (HOLD*, FREEZE, OVERRIDE, UNWIND) are untouched, and the integral only moves toward zero, never across. A new integral mode string must be classified on purpose.
- Early return that forces the output (guard cut, off) must publish an explicit `ctl.last_i_mode` (`I:OVERRIDE(...)`); a stale `I:RUN` makes anti-windup drain the integral against the forced zero.
- A bare `I:HOLD` can come from the latched deadband shell or a resume hold; never infer dead time from `i_mode` -> read `ctl.last_integral_hold_source` (`integral_hold_source` in diagnostics).
- Conditional integration applies to the total `FF + PI` command; FF1 uses the static gain b/a, so a perfect static FF still does not cancel a disturbance dynamically (actuator dead time).
- Guard cut/kick are HEAT only (`smartpi/guards.py`), inactive in the bootstrap (`is_bootstrap`, a running cut is released). Near-band auto sizing is HEAT only (`smartpi/deadband.py`); COOL uses a symmetric `near_band_deg`. Do not assume HEAT/COOL mirror behaviour in tests or benches; every extra HEAT cut ends a heat episode and re-opens the dead-time hold.
- Guard cut reset hysteresis = max(`NEAR_BAND_HYSTERESIS_C`, `GUARD_CUT_RESET_STEPS` x observed step) (`guards.sensor_step_c`), else a flickering 0.1 C reading re-triggers the cut.
- During a cut the integral unwinds only down to `Kp*(near_band_above - NEAR_BAND_HYSTERESIS_C)/Ki` (`algo.py::_unwind_integral_during_guard_cut`). Without unwinding the release restores the same power and the cut repeats; unwinding below the floor erases the real comfort-period integral and slows the next rise.
- The cut branch in `algo.py::calculate` must keep observing: dead-time estimator, `_last_current_temp` and learning (`_update_learning_during_guard_cut`, `skip: guard cut` for A). Returning early starves the best passive b windows (a setpoint decrease can hold the cut for hours). Its published error/anticipation come from `guards.cut_error` at the diagnostics boundary: never write `_last_error`, `_last_error_p` or the anticipation gate in the cut branch (the release would start from them).
- The anticipation (`smartpi/anticipation.py`) must stay off the deadband, guards, FF and learning: they read the measured temperature (`error`), only P and I read `Tin + c` (`error_p`, `error_i_ctl`). It is 0 outside the STABLE phase; do not feed it with a filtered temperature (slope on `dt_est.tin_history` raw samples) nor let it act without a reliable horizon (`anticipation_horizon_source` `none` means no correction).
- The fade of the correction (`w`) is what lets the room land: a correction kept at full size near the setpoint holds the room below it. HEAT and COOL use the same rule (the correction is added to the temperature, whatever the mode); the heating-balance emitter lag is the horizon in HEAT only. There is no post-PI cap and no shaped setpoint.
- A directional/non-directional integral block after a setpoint change can pin a steady error (P-only equilibrium = deficit/Kp) or create a catch-22 with opposing integral memory; any hold must be signed and let opposing memory unwind to zero.
- Resume after window/shedding holds the integral for the effective dead time (`smartpi/resume_hold.py`); a resume with small residual error ends the hold early.
- HEAT<->COOL: `calculate` resets the PI and calls `est.ensure_hvac_mode`; model is signed mono-mode (a>0 HEAT, a<0 COOL, b>0). Legacy COOL states used a positive A: the migration keeps b and resets A. A mode change stashes the outgoing mode-dependent model (a channel, dead times, emitter lag) and restores the incoming one; `ensure_hvac_mode` still returns True then, so the PI/FF warm-up restarts. Tests must not switch mode on a prepared model (A history is cleared).
- Dead-time channels are physical: `deadtime_heat` = temperature rise, `deadtime_cool` = fall; map the active one through the current mode (`active_deadtime`, `active_slot`); the other slot is always empty, so never read `deadtime_cool_*` in HEAT. Published `model.deadtime_*` and `analysis.deadtime.*_last_outcome` keys follow the mode.

## Learning windows A/B and dead time

- Learning slopes must use raw quantised samples (`dt_est.tin_history`); an EMA inflates `jumps`/`n_eff` in `ABEstimator.robust_dTdt_per_min`. Window anchor/amplitude use `t_int_clean`; dead-time detection uses filtered `t_int_lp` (`smartpi/tint_filter.py`).
- Phase `Calibration` lasts only while a calibration pulse commands the output (`LearningStart.phase`): the handler forces a scheduler cycle at every calculation in that phase, so a phase spanning the PI regulation between pulses would restart the PWM cycle at each tick.
- The calibration end check reads `calibration_reading(cal.mode)` before `Calibration.check` sets the mode: an agreeing reading is seen from the second calculation of a calibration (tests inject the reading after one tick).
- A `b` corrected by a calibration clears `b_meas_hist`: `LearningStart.b_waiting` (bootstrap) also accepts a standing `b`, or the bootstrap start would return to its learning stage and cancel the calibration.
- A pulse's heating step must wait for the dead-time detector while the gains read the dead time after a start: a rise of 3 sensor steps alone (0.03 C at 0.01 C) ends it before the 0.05 C detection on the filtered temperature, the cut aborts it (a calibration pulse lost its dead time in 4 min of heating).
- Passive b windows wait theta + tau_e after the cut (`smartpi/power_steps.py::PowerSteps.passive_gate_end`) and count the residual delivered power in `b` with the usable `a`; the a <-> b replays must stay one per published change (`ABEstimator._follow_a`, `_replay_a_measurements`): never let a replay call the other one. In the learning stage no window opens without the mode's model: a room whose fits are all rejected stays in the stage.
- First `b` windows after a cut counted p = 0 when the response model was first published after the cut (bootstrap: the event closes after the peak): the delivered-power filter restarted from the applied power, though a one-hour emitter still gave 18-30 % (bench: `b` -39..-62 points, `a` -46 % at the bootstrap exit) -> `PowerSteps` keeps the applied command history and rebuilds the filter over it at the first model (`_rebuild_filter`), and a model change recomputes the `b` obs power from it (`window_power`). Never restart the filter from the applied power except after an unobserved stretch, and keep the forward filter and `window_power` on the same rule (start of the history = steady at its first command).
- ON/A windows are blocked on the exact setpoint-change tick and while a setpoint transition is active (`a_learning_block_reason`, `skip: setpoint transition`); the gate is rechecked on effective duty before submission (a window can start passive and turn active). Do not block the preceding active ascent (natural A excitation). OFF/B stays exempt.
- An observation gap (guard cut, restart) must not mix pre/post-gap samples: dt is capped at one cycle and the window closes at the last observation; contiguity after a cut uses `_guard_cut_learning_ts`.
- Governance freezes thermal learning on `regime_transition` as soon as two regimes appear in one cycle and on DEAD_BAND (`smartpi/governance.py`). Near equilibrium only a/b is identifiable; admitting DEAD_BAND measurements biases a by about -35 %. Do not relax these freezes to "learn more".
- Bootstrap: active windows are capped at `AB_SETTLE_ACTIVE_CAP_FRAC` x median heating phase; a rule of "active window >= one PWM cycle" blocks the bootstrap whenever the cycle exceeds the heating phase.
- `ABEstimator.a_model_ready` defaults True; `algo.py` sets it False at reset and from `learn_win.a_model_ready` after `_start.load` in `load_state` (the model loads with `LearningStart`, after `lw_state`). Without that, `algo.phase` reads STABLE on the first tick after a restart (dt_min=0) and the bootstrap hysteresis keeps the PI output.
- Dead-time timeout: 4 h after a start (`DEADTIME_ACTIVE_TIMEOUT_S`); `DT_MAX_MIN` is deliberately unchanged (windows, emitter lag).
- Slow sensors (0.1 C, 15-60 min heartbeat): bootstrap stays in hysteresis long; learned dead time = sensor period for periodic samplers; b is biased low by first-significant OLS stopping on windows covering < ~1.5 steps (span guard). Reverting to EMA or `OLS_MIN_JUMPS=2` is not a fix.
- `AB_DRIFT_MAD_FLOOR_ABS` (1e-4) is larger than real b (1e-4..3e-4): b outlier gating is nearly inactive. Mild-weather b is biased low (free gains); do not calibrate on it.
- a/b outlier gate: the tolerance is 3 x 1.4826 x MAD of the history, with an absolute floor (`AB_DRIFT_MAD_FLOOR_ABS`) and a relative floor (`AB_MAD_REL_FLOOR`, 2 % of the history median). Without the relative floor a tight early `a` history rejected honest samples and locked the learning (one draw: 10th own `a` at 194 h instead of 28 h, guard band left at its 0.16 C fallback, overheat cuts doubled in a light-mass one-hour-emitter room). The lock was seen with the direct start, almost never in bootstrap (no lock in 24 bootstrap runs of the bench). For `b` the relative floor stays under the absolute one.
- Reading the measurement events: the first window of a reading must end at the close of its event (peak confirmed), not at the peak itself, and the power channel of a switch must hold the real on/off edges from the receipts (a cycle fraction held over a cycle blurs the step); both gaps gave a biased `b` in a bench. A starting value is not a measure: it writes no history and no counter, and the feed-forward ramp reads `ramp_count` (latched credit), never `learn_ok_count`, so a release cannot make it drop.
- Defaults a=0.0005 / b=0.001 mean "nothing learned"; exclude such rows (`learn_ok_count`) from bias statistics.
- Delivered-power model: ON/A uses a first-order power model with the dead time as a pure dead time; emitters with dead time + inertia structure or slow emitters (>= 20 min) bias a low; the emitter lag (theta + tau_e, symbol `T_ar` in `theory.md`) is a first moment, not a dead time. Changing this model needs a multi-emitter bench, not one plant.
- Room history (`smartpi/room_history/`) and room model (`smartpi/room_model/`) are active (`handler.py` builds `SmartPI(room_model=True)`) but HEAT only, no valves (`HISTORY_VALVE_MODE_SUPPORTED = False`), and need numpy/scipy (manifest requirements, lazy import in executor jobs: `deps.dependencies_importable`; history is not recorded when they are missing). The gains never read a learned emitter lag: they read the dead time after a start. Rule constants in `room_history/const.py` and `room_model/const.py` are validated methods, not knobs.
- Night/morning estimates are biased by unmodelled gains (sun, sleepers) and by mass rooms (air-wall coupling): only quiet periods are used (`smartpi/quiet_periods/`: darkness via `solar.py`, setback runs, regulated start), disturbed windows are excluded rather than modelled. No clock-span or occupancy schedule belongs in the code.
- Response model, weak dark event replacing a good daytime one: a fit on a rise of 0.03-0.05 C (3-5 steps of a 0.01 C sensor) gave S of 100-460 s against about 1200 s, and, being in darkness, it replaced the daytime bootstrap event (`smartpi/response_model.py` drops the daytime events at the first dark one); the published horizon fell for days and the overshoot doubled -> `smartpi/event_fit.py` rejects a rise under max(`FIT_MIN_RISE_STEPS` sensor steps, `FIT_MIN_RISE_C` = 0.10 C); keep both floors.
- Response model, one regulation event reading the slow mode of the room: in a bedroom occupied at night one event fitted S of about 9900 s (dead time assumed) against a seed of about 300 s, replaced the seed, and the anticipation horizon (slope x H) acted as a huge derivative: limit cycle of about 40 min, near band at its 2 C ceiling -> an event outside [S_ref/2, 2 S_ref] stays pending until a second one on the same side agrees with it (`ResponseModel._place`), and a model saved before that rule is replayed from the recomputed seed at load (`ResponseModel.repair`). Never let a single event move the published S by more than a factor 2.

## Feed-forward

- No outdoor temperature = FF1 off (`smartpi/feedforward.py`, `ff_no_ext_temp`). `analysis.feedforward.u_ff_final` and `u_ff_effective` are published equal to `u_ff1`: no other term is added to the holding power.
- FF1 warmup scale = `learn_ok_count/ff_warmup_ok_count` x cycle ramp. A state with fewer than `ff_warmup_ok_count` accepted learnings (30) and no further learning keeps a reduced FF forever; seeded test/bench states must set the counts.
- The room model never changes FF1 or any other regulation input: FF1 is the learned b / a only. The one discrete change of FF1, a calibration correction of `a` or `b`, is moved into the integral (`I <- I - dU/Ki`, `LearnedStepTransfer`) to keep the command continuous. Indirect link left in place: the restart bridge reads the last tick of the room model store (`SmartPI._restart_stores`) when it decides whether a stop is bridged.
- Restart bumpless contract: `load_state` restores the integral, so every FF factor (`cycles_since_reset`, learn scale, `ff_source`/`ff_wall`) must also come back; an FF restarting from zero against a restored integral gives a dip then an overshoot.

## Persistence and restart

- `state_store.py`: `STORAGE_KEY` with legacy fallback `LEGACY_STORAGE_KEY` (migrated on load; removing it loses learning of existing installs). `Store.async_delay_save` re-arms on every call: never call it per tick; use `SmartPIStateStore.schedule_save` (own deadline). The room history and the room model use their own stores and delays. The history store keeps the storage key suffix `.tar_learning` (existing installs); do not rename it.
- Algorithm state belongs in `SmartPI.save_state/load_state` (nested, versioned), not ad hoc in the handler. Loaders must tolerate obsolete keys (e.g. old restart contexts).
- Time conversion: `convert_monotonic_to_wall_ts`/`convert_wall_to_monotonic_ts` are DEADLINE helpers (expired -> None); past events use `monotonic_to_wall_ts`/`wall_to_monotonic_ts`, whose result can be negative after a host reboot: compare to `None`, never to zero (`smartpi/timestamp_utils.py`).
- Monotonic timestamps are cleared in OFF and cannot measure downtime: prolonged-OFF expiry uses persisted `last_active_wall_ts` from the last valid active tick; OFF calculations must not refresh it.
- Restart bridge (`smartpi/restart_bridge.py::decide`): a stop <= `RESTART_BRIDGE_MAX_GAP_S` with same mode/cycle config, saved actuator state, no exclusion and a plausible first temperature is bridged (VT sends no command at stop or start, the heater keeps its state); otherwise conservative resets. The decision waits for the first indoor temperature; meanwhile `command_holdable` keeps the pre-stop command. The bootstrap hysteresis output is restored only after a bridged restart in the same mode. The room history and the room model bridge only in HEAT.
- `dt_est.tin_history` is persisted (wall time), the emitter-lag tail and late crossings survive a restart.

## VT/HA integration and applied-command receipts

- VT calls `SmartPI.calculate(target, current, ext, slope, hvac_mode, ...)` positionally from `recalculate`: never reorder; new arguments go last with defaults. Tests mock `recalculate` and hide such contracts (`tests/test_smartpi_vt_recalculate_contract.py`); dead-code inventories must grep VT callers (`_prop_algorithm`, handler/algo methods), not just SmartPI tests.
- `SmartPI.calculate` keeps `cycle_boundary` and `temperature_measure_id` in its signature (VT calling contract) although the regulation does not read them.
- Applied power: SmartPI sends `start_cycle(hvac_mode, on_percent, force)` with no request tag and reads the scheduler's applied-command receipts (`vtherm_api.command_receipt`, `register_command_receipt_callback` -> `algo.on_command_receipt`). The receipt carries the applied actuator power, which may differ from the request (min on/off delays, valve retention).
- A valve opening retained by VT (dpercent/period filter) comes back in the receipt as the applied position. Learning follows VT's committed command (`_commit_applied_command` -> `_committed_on_percent`), not a measured mechanical position. Without receipts the handler falls back to the legacy cycle callback and reads `thermostat.valve_open_percent` (`handler.py::_published_valve_power`).
- Valve linearization needs both gates: SmartPI option and scheduler valve mode. VT post-processes the opening (dpercent filter, period filter, opening remap from "min opening"); `valve_config_check.py` only observes and raises Repairs, it never alters regulation. Do not prescribe a 0 regulation threshold (some TRVs need >= 3 %); a radiator activation opening belongs in SmartPI `smart_pi_min_valve`.
- Device linking: entities attach through `Entity.device_entry` (`async_entity_id_to_device`); never copy VT identifiers/connections into `device_info`, never add/remove SmartPI config entries on VT devices; cleanup lives in `smartpi/device_link.py` and must keep every source device id of a global multi-target entry. HACS minimum HA is 2025.8 for this reason.
- A disabled dedicated entry still counts as dedicated (`sensor.py::_get_dedicated_target_unique_ids`): its diagnostic sensor stays disabled, regulation falls back to the global config. Stale device bindings need explicit cleanup.
- Sensor health is VT's job: SmartPI never declares a sensor stale.

## Diagnostics and schema

- Publish only through `smartpi/diagnostics.py::build_published_diagnostics`; add a field in the `_build_<section>` of its section from SmartPI state (no flat intermediate dict). Tests read `algo.get_published_diagnostics()` (nested live tree); normal and debug use the same tree.
- Key paths are pinned by `tests/fixtures/published_diagnostics_paths.json` (`tests/test_published_diagnostics_schema.py`); regenerate with `SMARTPI_UPDATE_DIAG_PATHS=1` only for an intended schema change, then adapt the Equinox card, `cards/*.md`, `documentation/*/diagnostics.md`.
- The schema pin covers `room_model.*` (the test builder uses `room_model=True`): a changed path there needs the fixture regenerated, and a check by hand against cards, docs and Equinox.
- Equinox (external Lovelace card) reads published names (`specific_states["regulation_diagnostics"]`, live paths, history series). Renaming/removing a field breaks it silently; governor, landing and setpoint-trajectory fields are gone and asserted absent, so a card still reading them shows blanks until adapted.
- Envelope `{schema_version, live, history}` is built in `smartpi/diagnostic_history.py`. `history` is a fixed set of Recorder series; the builder indexes `control/temperature/setpoint/power/model` live keys strictly (test doubles must carry them) and reads feedforward/room_model blocks with `.get` (null when missing).
- Recorder attribute exclusion is static class metadata merged at subclass creation: `SmartPIDiagnosticSensor` excludes `live`, `SmartPIRecordedDiagnosticSensor` records it; never mutate `_unrecorded_attributes` on an instance. Exclusion does not stop `states` rows from changing live-only attributes: keep handler dispatch gating (`smartpi_diag_update_{id}` only for meaningful inputs, cycle boundaries, forced calculations, services) and the sensor's identical-write suppression; `force_update` or an unconditional timer dispatch recreates the churn.
- Published user-facing values stay plain: no internal codes or rule names; translate at the diagnostics boundary.
- Analysing exports: `live.temperature.indoor` is the last calculation's sensor temperature, `history.temperature.indoor` is its copy, climate `current_temperature` is a different thing. It stops refreshing while VT is off. HA REST history needs `significant_changes_only=0` to return attribute-only sensor rows; two rows versus thousands of climate rows is not proof of lost Recorder data.
- Markdown cards: guard `states[entity_id] is not none` (a missing entity returns the truthy string `unknown`); read `live.control.in_near_band` instead of recomputing bounds; show `live.learning.enabled` independently of progress/governance.

## Config flow and translations

- Effective config (`handler.py::_resolve_effective_config`): `DEFAULT_OPTIONS` < thermostat `entry_infos` < ONE of the dedicated entry (`CONF_TARGET_VTHERM` = VT unique id) or the global entry (`unique_id == DOMAIN`); disabled entries excluded; entry `data` then `options`.
- Global and dedicated flows share `SmartPIOptionsFlow.async_step_init` and the `options.step.init.title`: keep it generic ("SmartPI settings"/"Parametres SmartPI"), never mode- or target-specific.
- Valve options depend on VT target type/attributes (`config_flow.py`, `valve_config_check.py`); changing detection logic affects both the global and per-target flows. VT shows its valve filters in the "Underlyings" menu, not "Valve regulation configuration".
- HA strings live only in `translations/en.json` and `translations/fr.json` (config/options steps, services, exceptions, issues `dpercent_filter/period_filter/opening_remap/vtherm_version`); they are separate from `README*.md` and `documentation/{en,fr}`. A new option/service/issue needs both JSON files, `services.yaml`, docs EN+FR.
- Docs describe the current state only (no "new"/"changed"); code comments and docs in English; no plan, bench or review identifiers in comments.

## Tests and benches

- Tests need `vtherm_api/src` and `versatile_thermostat` as siblings of the repo (`tests/conftest.py`: `WORKSPACE_ROOT = REPO_ROOT.parent`). A git worktree elsewhere needs those two directories (or symlinks) next to it; even then `tests/test_config_flow.py` and `tests/test_init_lifecycle.py` fail with "Could not setup dependencies: versatile_thermostat" unless run from the main checkout.
- Bench drivers and scenario files are local and gitignored (not in the repository). Comparing two code versions needs one worktree per ref with the local drivers copied in; verify each arm imports SmartPI from its own tree (print `module.__file__`) or both arms silently run the main tree.
- Clocks: simulated runs patch `time.time` AND `time.monotonic` globally (`tests/regulation_sim.py`); restart tests too (`DeadTimeEstimator.load_state` sets `last_stop_time` from monotonic; timestamp helpers read both). Production code must call `time.monotonic()` through the module so patches apply.
- Bench drivers hook SmartPI private names on the instance; after moving a method keep internal calls going through `self.<name>` so the hook sees every call.
- Bit-identity pins: `tests/fixtures/regulation_reference.json`, `tests/test_regulation_reference.py` (sha256 of a closed-loop run, option off) and `tests/test_room_model_regulation.py`. Any change of regulation output breaks them; regenerate only for an intended behaviour change.
- Learning in tests is cycle-bound: mid-cycle changes publish diagnostics without committing windows. `tests/helpers.py::force_smartpi_stable_mode` seeds histories; `make_receipt` builds scheduler receipts.
- Frozen-model benches seeding a/b histories start STABLE and never learn the dead time (no bootstrap steps): inject the dead time or compare end-to-end cold starts. A closed-loop run that seeds an integral must also declare and restore the Ki that owns it (before I) and give the plant the committed-power prehistory.
- Bench plants: a_true = 60*P/C (per min) must stay below `ABEstimator.A_MAX` (0.5); hold power must stay in [0.05, 0.95] across all scenarios; use >= 10 seeds to resolve +-0.1 on a median; restrict bias statistics to runs with `learn_ok_count > 0`.
- A PWM on and an off edge at the same instant are a zero-length pulse (merge them; sorting by value turns it into a full cycle).
- Disturbance-rejection comparisons under PWM: subtract a phase-matched undisturbed trajectory and sample several settled start cycles. A rule written against one BASE (e.g. "integral below BASE") must be re-derived when BASE already has a mechanism of that kind.
- Offline replays with numpy in a process pool: set `OMP_NUM_THREADS=1`/`OPENBLAS_NUM_THREADS=1` or workers oversubscribe and stall; `ProcessPoolExecutor(max_tasks_per_child=...)` deadlocked, use one process per run. Count finished runs from result files, not from a log appended by several processes.
- Job waiting: run long jobs in the background and wait for the completion notification. Never poll, never loop on `pgrep -f <pattern>` (it matches its own command line); if waiting by script, wait on a PID or a log marker with a hard timeout. One bench at a time (CPU). zsh does not word-split `$var`: use `sh` scripts for job lists. WSL/NTFS makes the full suite slow.
- Harness published values must follow the declared sensor quantum (round to the quantum, not to 1 decimal), otherwise any quantum below 0.1 C is silently 0.1 C; outdoor is rounded separately.

## Sensors

- Target = precise sensors (0.01 C, publish on change, ~5 min heartbeat). 0.1 C on change with a 30/60 min heartbeat is best effort; a bench model with 300 s sampling only is unrealistic.
- Observed quantum = smallest raw step (`learn_win.balance.resolution_c`, `ab_window_balance.py`); it sizes the guard reset hysteresis and the near-setpoint unwind band.
- Publish-on-change sensors: only level crossings carry timing. A one-step change is the midpoint of the two levels, a multi-step change is a sampled value (`smartpi/event_fit.py::crossings`); held values between changes have no known time. Held values form a staircase whose OLS slope is biased low by `(1 - 1/m^2)` over m levels, and an episode triggered by a measured threshold biases the values just before it by up to half a step.
- A heartbeat repeats a value: it carries no information. The room-model observer corrects only on a new, different value; `dt_est.tin_history` adds a point on change or after 60 s.
- `ab_window_balance.py` pools raw-step integral balances for coarse sensors; a window must be monotone and last `AB_BALANCE_MIN_SEGMENT_MIN`; its uncertainty model (half a step per end) breaks with noise at the scale of a step.
- Sensor noise bound is separate from quantisation: never widen gates after observing a result; keep 0.1 C a separate bench axis from bounded noise.

## Removed code (do not look for it)

`SmartPIIntegralGuard` and its setpoint-change/disturbance-recovery integral guards (`I:GUARD`), the setpoint/reference governor (post-PI cap, GOVERNED/HANDOFF states, nominal-guard profile), `governor_*`/landing diagnostics, flat/debug diagnostics API, `CausalThermalBalanceAdmission`/`evaluate_causal_thermal_balance`, energy-balance FF knob (`SMARTPI_ENERGY_BALANCE_FF`), `SmartPI._gain_generation` and the gain generation counter, `apply_integral_power_transfer`, model-inverting landing caps, the FF2 trim (`ff_trim*.py`, causal power trace, thermal measurement source), FF3 (`ff3*.py`, option `use_ff3`), the 1R1C thermal twin with its time-to-setpoint estimate, command ownership (`command_ownership.py`, `stage_command`, request ids).
